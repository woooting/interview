# TCP 和 UDP

## 核心区别

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接方式 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠传输（确认、重传、排序） | 不可靠，尽最大努力交付 |
| 有序性 | 保证字节流有序 | 不保证 |
| 流量控制 | 滑动窗口机制 | 无 |
| 拥塞控制 | 慢启动、拥塞避免、快重传、快恢复 | 无 |
| 头部开销 | 20字节（最小） | 8字节 |
| 传输方式 | 字节流 | 数据报 |
| 通信模式 | 点对点 | 一对一、一对多、多对多 |

---

## 操作系统层面

### Socket API 差异

**TCP（SOCK_STREAM）：**
```
socket() → bind() → listen() → accept() → read()/write() → close()
```
- 内核为每个 TCP 连接维护**发送缓冲区**和**接收缓冲区**
- `write()` 只是将数据拷贝到发送缓冲区，真正发送由内核协议栈决定（Nagle 算法可能合并小包）
- `read()` 从接收缓冲区读取，读取的字节数可能少于请求数（流式特性）

**UDP（SOCK_DGRAM）：**
```
socket() → bind() → sendto()/recvfrom()  （无需 listen/accept）
```
- 内核不维护连接状态，每次发送需指定目标地址
- `sendto()` 将完整数据报交给内核，内核直接封装发送
- `recvfrom()` 一次读取一个完整数据报，超出则截断丢弃

### 内核协议栈处理流程

```
应用层数据
    ↓
TCP: 分段 → 加序号 → 计算校验和 → 等待确认/重传
UDP: 直接加8字节头 → 计算校验和（可选） → 立即发送
    ↓
IP层: 加IP头 → 路由选择
    ↓
链路层: 加帧头帧尾 → 物理发送
```

### 关键内核参数

- `tcp_rmem` / `tcp_wmem`：TCP 接收/发送缓冲区大小（min, default, max）
- `somaxconn`：listen 队列最大长度
- `tcp_tw_reuse`：TIME_WAIT 状态复用
- `udp_rmem_min` / `udp_wmem_min`：UDP 缓冲区最小值

## 浏览器与服务端的通信

### HTTP/1.1 和 HTTP/2（基于 TCP）

```
浏览器发起请求流程：
1. DNS 解析（UDP 53 端口查询域名 → IP）
2. TCP 三次握手（SYN → SYN+ACK → ACK）
3. TLS 握手（如 HTTPS：ClientHello → ServerHello → 证书交换 → 密钥协商）
4. 发送 HTTP 请求（GET/POST 等）
5. 接收 HTTP 响应
6. TCP 四次挥手关闭连接（或 Keep-Alive 复用）
```

**HTTP/2 多路复用：** 单个 TCP 连接上并行发送多个请求，通过 Stream ID 区分，解决了 HTTP/1.1 的队头阻塞问题。但 TCP 层的队头阻塞仍然存在——一个丢包会阻塞该连接上所有流。

### HTTP/3（基于 UDP + QUIC）

```
QUIC 协议栈：
应用层 (HTTP/3)
    ↓
QUIC 层（用户态实现，基于 UDP）
    ↓
UDP
    ↓
IP
```

**QUIC 解决的核心问题：**
- **消除 TCP 队头阻塞**：每个 Stream 独立重传，一个 Stream 丢包不影响其他 Stream
- **0-RTT 连接建立**：首次连接 1-RTT，后续连接可 0-RTT 恢复（对比 TCP+TLS 需要 2-3 RTT）
- **连接迁移**：通过 Connection ID 而非四元组标识连接，WiFi 切 4G 连接不断

**浏览器实际行为：**
- Chrome/Firefox 优先尝试 HTTP/3（UDP 443），失败后 fallback 到 HTTP/2（TCP）
- DNS 响应中的 HTTPS 记录（SVCB/HTTPS RR）会告知服务端是否支持 HTTP/3

### DNS 解析中的 TCP 与 UDP

- **常规查询**：UDP 53 端口，响应 ≤ 512 字节
- **响应过大**：服务端设置 TC（Truncated）标志，客户端改用 TCP 重试
- **区域传送（AXFR）**：强制使用 TCP
- **DNS over TLS (DoT)**：TCP 853 端口
- **DNS over HTTPS (DoH)**：TCP 443 端口（底层走 HTTPS）

## 应用场景

### TCP 适用场景
- **Web 浏览**：HTTP/1.1、HTTP/2（要求数据完整）
- **文件传输**：FTP、SFTP（不允许丢字节）
- **邮件**：SMTP、IMAP、POP3
- **远程登录**：SSH、Telnet
- **数据库**：MySQL、PostgreSQL（事务完整性）

### UDP 适用场景
- **实时音视频**：Zoom、WebRTC（延迟敏感，允许少量丢包）
- **在线游戏**：FPS/MOBA（状态同步，过期数据无意义）
- **DNS 查询**：快速小数据包
- **QUIC/HTTP/3**：现代 Web 加速
- **IoT/传感器**：低开销、周期性上报

---

## 本质思考

TCP 和 UDP 的选择本质是**可靠性与实时性的权衡**：

- TCP 在不可靠的 IP 层之上构建了可靠的字节流抽象，代价是延迟（握手、确认、重传、拥塞等待）
- UDP 几乎不做任何保障，将控制权完全交给应用层，换取最低延迟
- QUIC 的出现代表了一种趋势：**将传输层逻辑从内核移到用户态**，基于 UDP 重新实现可靠传输，既保留 UDP 的灵活性，又通过应用层实现获得 TCP 的可靠性，且可快速迭代（无需等待内核更新）

# HTTP 协议演进：1.0 → 1.1 → 2 → 3

## 版本关系总览

```
HTTP/1.0 (1996)  ──→  HTTP/1.1 (1997)  ──→  HTTP/2 (2015)  ──→  HTTP/3 (2022)
  短连接               长连接+管线化          多路复用+二进制帧        QUIC+UDP
  文本协议              文本协议               二进制协议               二进制协议
  基于TCP              基于TCP               基于TCP                基于UDP(QUIC)
```

每次升级的核心驱动力：**降低延迟，提升传输效率**。

---

## HTTP/1.0（1996）

### 工作方式

```
请求1 → TCP握手 → 发送请求 → 接收响应 → TCP断开
请求2 → TCP握手 → 发送请求 → 接收响应 → TCP断开
请求3 → TCP握手 → 发送请求 → 接收响应 → TCP断开
```

每个请求/响应对都需要一个独立的 TCP 连接，完成后立即断开。

### 核心问题

**1. 连接建立开销巨大**

一个网页包含多个资源（HTML、CSS、JS、图片），每个资源都要：
- TCP 三次握手：1 RTT
- TLS 握手（HTTPS）：额外 2 RTT
- 假设 RTT = 50ms，加载 10 个资源 = 10 × (50 + 100)ms = 1500ms 仅用于握手

**2. 无法并行请求**

浏览器为缓解此问题，会对同一域名开启 6-8 个并行 TCP 连接，但：
- 每个连接独立做拥塞控制，无法共享带宽信息
- 大量连接消耗服务端文件描述符和内存（每个连接内核分配 ~4KB 发送缓冲区 + ~4KB 接收缓冲区）

**3. 无 Host 头字段**

HTTP/1.0 请求中没有 Host 头，导致一台 IP 只能部署一个站点，无法实现虚拟主机。

---

## HTTP/1.1（1997）——解决连接复用问题

### 解决的问题与方案

**问题1：每次请求都要重新建立 TCP 连接**

**方案：持久连接（Keep-Alive）+ 管线化（Pipelining）**

```
持久连接（默认开启）：
请求1 → TCP握手 → 发送请求 → 接收响应 → 发送请求2 → 接收响应2 → ... → TCP断开

管线化：
请求1 → TCP握手 → 发送请求1+请求2+请求3 → 接收响应1 → 接收响应2 → 接收响应3 → TCP断开
```

- `Connection: keep-alive` 使 TCP 连接复用，避免重复握手
- 管线化允许在收到响应前连续发送多个请求

**问题2：无法虚拟主机**

**方案：引入 Host 请求头**

```http
GET /index.html HTTP/1.1
Host: www.example.com
```

使得同一 IP 上的 Nginx/Apache 可根据 Host 头路由到不同站点。

**问题3：大文件传输中断需全量重传**

**方案：断点续传（Range 请求）**

```http
GET /video.mp4 HTTP/1.1
Range: bytes=1024-2047

HTTP/1.1 206 Partial Content
Content-Range: bytes 1024-2047/8192
```

**问题4：缓存控制粗糙**

**方案：引入精细缓存机制**

| 机制 | 说明 |
|------|------|
| `ETag` / `If-None-Match` | 基于内容指纹的条件请求 |
| `Last-Modified` / `If-Modified-Since` | 基于时间的条件请求 |
| `Cache-Control: max-age` | 明确缓存有效期 |
| `no-cache` / `no-store` | 精细控制缓存行为 |

**问题5：传输效率低**

**方案：分块传输编码（Chunked Transfer Encoding）**

```http
Transfer-Encoding: chunked

7\r\n
Mozilla\r\n
9\r\n
Developer\r\n
0\r\n
\r\n
```

服务端无需预知 Content-Length，可边生成边发送。

### HTTP/1.1 遗留问题

**队头阻塞（Head-of-Line Blocking）：**

```
管线化下的队头阻塞：

发送：请求1 → 请求2 → 请求3
接收：响应1（慢，3秒）→ 响应2（快，10ms）→ 响应3（快，10ms）

请求2和3的响应虽然已就绪，但必须等请求1的响应返回后才能按序发送。
```

管线化要求响应严格按请求顺序返回。如果第一个请求处理慢（如复杂 SQL 查询），后续所有请求都被阻塞。因此主流浏览器**默认关闭了管线化**，实际上退化为"持久连接 + 串行请求"。

**文本协议解析低效：**

HTTP/1.1 是纯文本协议，请求头可达数 KB（含 Cookie、User-Agent 等），解析需要逐行扫描、字符串匹配，容易出错且消耗 CPU。

## HTTP/2（2015）——解决队头阻塞与传输效率

基于 Google 的 SPDY 协议演进而来，是一次**根本性的协议重新设计**。

### 解决的问题与方案

**问题1：HTTP/1.1 应用层队头阻塞**

**方案：多路复用（Multiplexing）+ 流（Stream）**

```
HTTP/1.1（串行）：
|-- 请求1 --|-- 等待 --|-- 请求2 --|-- 等待 --|-- 请求3 --|

HTTP/2（多路复用）：
Stream 1: |-- 请求1 --------|
Stream 2:     |-- 请求2 --|
Stream 3:         |-- 请求3 --|
          全部在同一 TCP 连接上并行传输
```

- 每个请求/响应对是一个 Stream，有唯一 Stream ID
- 多个 Stream 的帧（Frame）可以交错发送，接收端按 Stream ID 重组
- 彻底消除了 HTTP/1.1 的队头阻塞

**问题2：文本协议解析低效且不安全**

**方案：二进制分帧层（Binary Framing）**

```
HTTP/2 帧结构：
+-----------------------------------------------+
|                 Length (24)                     |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+-------------------------------+
|R|                 Stream Identifier (31)                      |
+=+=============================================================+
|                   Frame Payload (0...)                      ...
+---------------------------------------------------------------+
```

- 所有数据被切分为二进制帧，不再是文本行
- 帧类型：HEADERS（压缩后的请求头）、DATA（请求体）、SETTINGS、PING 等
- 解析高效、无歧义，不易产生安全漏洞（如 HTTP 请求走私）

**问题3：请求头冗余大**

**方案：HPACK 头部压缩**

```
第一次请求发送完整头部：
:method: GET
:path: /index.html
:authority: www.example.com
cookie: session=abc123; theme=dark
user-agent: Mozilla/5.0...

第二次请求只需发送差异：
:path: /style.css
（其余头部引用静态/动态字典中的索引）
```

- 维护一个动态字典，常用头部（如 `:method: GET`）只需 1 字节索引
- 使用 Huffman 编码进一步压缩字符串值
- 典型场景下头部压缩率 > 80%

**问题4：被动推送，浪费 RTT**

**方案：服务端推送（Server Push）**

```
客户端请求 index.html
    ↓
服务端预判客户端还需要 style.css 和 app.js
    ↓
服务端主动推送 style.css 和 app.js（无需客户端再发请求）
```

减少了客户端发现资源依赖后的额外 RTT。但因浏览器缓存策略复杂，实际效果有限，Chrome 已默认禁用。

**问题5：资源优先级无法表达**

**方案：流优先级与权重**

```
HTML       → 权重 256（最高）
CSS        → 权重 220
JS（关键） → 权重 180
图片       → 权重 16（最低）
```

服务端可根据权重分配带宽，优先发送关键资源。

### HTTP/2 帧丢失与重传机制

**核心结论：HTTP/2 自身没有重传机制，帧丢失的重传完全由底层 TCP 协议栈负责。**

HTTP/2 的二进制帧在应用层被切分后，交给 TCP 作为字节流发送。TCP 不感知帧边界，它只看到一串连续的字节。因此，丢包检测和重传全部发生在 TCP 层（内核中），HTTP/2 层对此毫无感知。

#### 完整重传流程

```
发送端（服务端）                              接收端（浏览器）
    │                                           │
    │  TCP Segment 1 (seq=0, len=1400)          │
    │  包含: Stream1 HEADERS帧 + Stream2 DATA帧  │
    │ ──────────────────────────────────────────→ │  ✓ 收到
    │                                           │
    │  TCP Segment 2 (seq=1400, len=1400)       │
    │  包含: Stream1 DATA帧(前半部分)            │
    │ ─────────────────────────────────────────╳  │  ✗ 丢失
    │                                           │
    │  TCP Segment 3 (seq=2800, len=1400)       │
    │  包含: Stream1 DATA帧(后半部分) + Stream3  │
    │ ──────────────────────────────────────────→ │  ✓ 收到，但 seq 不连续
    │                                           │
    │                                           │  TCP 内核：发现 seq=1400 缺失
    │                                           │  → 缓存 Segment 3 到乱序队列
    │                                           │  → 发送 Duplicate ACK (ack=1400)
    │                                           │
    │  TCP Segment 4 (seq=4200, len=1400)       │
    │ ──────────────────────────────────────────→ │  ✓ 收到，仍然缺 seq=1400
    │                                           │  → 缓存 Segment 4
    │                                           │  → 发送 Duplicate ACK (ack=1400)
    │                                           │
    │  ← Duplicate ACK (ack=1400)               │
    │  ← Duplicate ACK (ack=1400)               │
    │  ← Duplicate ACK (ack=1400)               │  第3个重复ACK触发快重传
    │                                           │
    │  TCP 内核：收到3个重复ACK                   │
    │  → 触发快重传（Fast Retransmit）           │
    │  → 重传 Segment 2 (seq=1400)              │
    │ ──────────────────────────────────────────→ │  ✓ 收到缺失段
    │                                           │
    │                                           │  TCP 内核：seq 连续了
    │                                           │  → 按序交付 Segment 2,3,4 给应用层
    │                                           │  → HTTP/2 帧解析器一次性处理所有帧
    │  ← ACK (ack=5600)                         │
```

#### 关键细节

**1. TCP 不感知 HTTP/2 帧边界**

```
一个 TCP Segment 可能包含：
┌──────────────────────────────────────────┐
│ TCP Header (20 bytes)                    │
├──────────────────────────────────────────┤
│ Stream 1 HEADERS 帧 (部分)               │
│ Stream 2 DATA 帧 (完整)                  │
│ Stream 3 DATA 帧 (部分)                  │
└──────────────────────────────────────────┘

一个 HTTP/2 帧也可能跨多个 Segment：
Segment 1: [Stream1 DATA 帧前半部分]
Segment 2: [Stream1 DATA 帧后半部分]
```

TCP 按 MSS（Maximum Segment Size，通常 1460 字节）切分字节流，与 HTTP/2 帧的边界完全无关。一个 TCP 段可能包含多个帧的片段，一个帧也可能跨越多个 TCP 段。

**2. HTTP/2 层无法干预重传**

```
HTTP/2 层视角：
  发送帧 → 等待 → 帧被对端接收（或连接断开）
  没有超时重传、没有帧级 ACK、没有帧级序号

TCP 层视角（内核中）：
  发送字节 → 等待 ACK → 超时/重复ACK → 重传
  HTTP/2 对此过程完全不可见
```

HTTP/2 协议规范（RFC 7540）没有定义任何帧级别的重传、确认或序号机制。它完全信任 TCP 的可靠性保证。

**3. 丢包检测的两种方式**

| 方式 | 触发条件 | 延迟 |
|------|----------|------|
| **超时重传（RTO）** | RTO 定时器到期（初始约 1s，指数退避） | 高（至少 1 秒） |
| **快重传（Fast Retransmit）** | 收到 3 个重复 ACK | 低（约 1 RTT） |

```
超时重传场景（连续丢包，无后续数据触发重复ACK）：

发送 Segment → 丢失 → 等待 RTO（~1秒）→ 重传
→ 对端收到 → 返回 ACK

快重传场景（后续数据触发重复ACK）：

发送 Seg2(丢失) → 发送 Seg3 → 发送 Seg4 → 发送 Seg5
接收端对 Seg3/4/5 各返回 ACK(ack=Seg2.seq) → 3个重复ACK
→ 立即重传 Seg2（无需等超时）
```

**4. 重传期间的阻塞效应（TCP 队头阻塞的本质）**

```
时间线：

t=0ms    服务端发送 Segment 1,2,3,4,5（含 Stream 1,2,3 的帧）
t=10ms   Segment 2 丢失
t=20ms   浏览器收到 Seg 1,3,4,5 → 缓存 3,4,5 → 发重复 ACK
t=50ms   服务端收到 3 个重复 ACK → 快重传 Segment 2
t=60ms   浏览器收到重传的 Seg 2 → 按序交付 2,3,4,5 给 HTTP/2 层

在 t=20ms ~ t=60ms 这 40ms 内：
  - Stream 2 的帧在 Seg 3,4 中 → 已到达内核缓冲区
  - 但 TCP 不交付给应用层（因为 Seg 2 还没到）
  - HTTP/2 帧解析器看不到这些帧 → Stream 2 的响应被完全阻塞
  - 即使 Stream 2 的数据一个字节都没丢，也被 Stream 1 的丢包连累
```

这就是为什么 HTTP/2 的多路复用是"假并行"——应用层交错发送多个 Stream 的帧，但底层 TCP 的有序交付语义使得任何一个丢包都会阻塞同一连接上的所有 Stream。

#### 与 HTTP/3 (QUIC) 重传的对比

```
HTTP/2 + TCP：
┌─────────────────────────────────────────────┐
│  HTTP/2 帧层（无重传能力）                    │
├─────────────────────────────────────────────┤
│  TCP（统一重传，所有 Stream 共享一个序号空间） │
│  Seg 2 丢失 → 全部阻塞 → 重传 Seg 2          │
│  → Stream 1,2,3 全部等待                     │
└─────────────────────────────────────────────┘

HTTP/3 + QUIC：
┌─────────────────────────────────────────────┐
│  HTTP/3 帧层                                 │
├─────────────────────────────────────────────┤
│  QUIC（每个 Stream 独立序号、独立重传）       │
│  Stream 1 包丢失 → 仅重传 Stream 1 的包      │
│  Stream 2 的包正常交付 → 不受影响             │
│  Stream 3 的包正常交付 → 不受影响             │
└─────────────────────────────────────────────┘
```

QUIC 为每个 Stream 维护独立的 Packet Number 空间和重传队列。Stream 1 的丢包触发 Stream 1 的重传，Stream 2 和 Stream 3 的数据包被 QUIC 层直接解密交付给 HTTP/3 层，无需等待。

---

### HTTP/2 遗留问题：TCP 层队头阻塞

```
TCP 队头阻塞问题：

Stream 1 的数据包 P1 丢失
Stream 2 的数据包 P2 已到达

TCP 保证有序交付 → P2 必须等 P1 重传成功后才能交给应用层
→ Stream 2 被 Stream 1 的丢包阻塞

HTTP/2 多路复用在 TCP 之上，无法绕过 TCP 的有序性约束。
```

这是 HTTP/2 架构层面的根本限制——多路复用的优势被底层 TCP 的有序字节流语义抵消。丢包率越高，问题越严重（移动网络下 HTTP/2 有时甚至不如 HTTP/1.1 多连接）。

---

## HTTP/3（2022）——彻底摆脱 TCP 束缚

### 协议栈重构

```
HTTP/1.1 & HTTP/2:              HTTP/3:
┌─────────────┐                 ┌─────────────┐
│   HTTP      │                 │   HTTP/3    │
├─────────────┤                 ├─────────────┤
│   TCP       │                 │    QUIC     │
├─────────────┤                 ├─────────────┤
│   IP        │                 │    UDP      │
├─────────────┤                 ├─────────────┤
│  Ethernet   │                 │    IP       │
└─────────────┘                 ├─────────────┤
                                │  Ethernet   │
                                └─────────────┘
```

HTTP/3 不再使用 TCP，而是基于 **QUIC（Quick UDP Internet Connections）** 协议，QUIC 运行在 UDP 之上。

### 解决的问题与方案

**问题1：TCP 层队头阻塞**

**方案：QUIC 独立 Stream + 独立重传**

```
TCP（HTTP/2 底层）：
Stream 1 包丢失 → 整个 TCP 连接阻塞 → 所有 Stream 等待重传

QUIC（HTTP/3 底层）：
Stream 1 包丢失 → 仅 Stream 1 等待重传
Stream 2 数据正常交付 → 不受影响
Stream 3 数据正常交付 → 不受影响
```

QUIC 在 UDP 之上实现了类似 TCP 的可靠性，但每个 Stream 有独立的丢包检测和重传机制。一个 Stream 的丢包不会阻塞其他 Stream。

**问题2：连接建立延迟高（TCP 握手 + TLS 握手）**

**方案：QUIC 内置 TLS 1.3 + 0-RTT 恢复**

```
HTTP/2 首次连接：
TCP 三次握手 (1 RTT) + TLS 1.3 握手 (1 RTT) = 2 RTT 后才能发 HTTP 请求

HTTP/3 首次连接：
QUIC 握手 + TLS 1.3 合并 = 1 RTT 后即可发 HTTP 请求

HTTP/3 后续连接（0-RTT）：
客户端缓存服务端传输参数和 TLS 会话
→ 第一个包同时携带握手数据和 HTTP 请求 = 0 RTT
```

| 场景 | HTTP/2 | HTTP/3 |
|------|--------|--------|
| 首次连接 | 2 RTT | 1 RTT |
| 恢复连接 | 1 RTT（TLS Session Resumption） | 0 RTT |

**问题3：网络切换导致连接断开**

**方案：Connection ID 标识连接**

```
TCP 用四元组标识连接：(源IP, 源端口, 目标IP, 目标端口)
→ WiFi 切 4G 时源 IP 变化 → 四元组不匹配 → 连接断开 → 需重新握手

QUIC 用 Connection ID 标识连接：
→ Connection ID 与 IP 无关
→ WiFi 切 4G 后发送 Connection ID → 服务端识别为同一连接 → 无缝继续
```

这对移动设备尤其重要——地铁、电梯等场景下网络频繁切换，HTTP/3 可保持连接不断。

**问题4：TCP 协议在内核中难以升级**

**方案：QUIC 在用户态实现**

```
TCP：运行在操作系统内核中
→ 升级需等待 OS 更新（Windows Update、Linux 内核升级）
→ 周期以年计

QUIC：运行在用户态（如 Chromium 内置、Nginx 模块）
→ 随应用更新，浏览器自动升级即可使用新版 QUIC
→ 迭代周期以周计
```

这也是为什么 QUIC 选择基于 UDP——UDP 在内核中只做最简单的转发，复杂逻辑全在用户态 QUIC 库中实现。

**问题5：中间设备（Middlebox）干扰**

**方案：QUIC 头部加密**

```
TCP：头部明文 → 中间设备可修改序列号、窗口大小 → 导致协议僵化
QUIC：除极少数字段外，所有头部和载荷均加密 → 中间设备无法窥探或篡改
```

这解决了 TCP 的"协议僵化"问题——很多中间设备（防火墙、NAT、运营商设备）会检查甚至修改 TCP 头部，导致新的 TCP 扩展（如 TCP Fast Open）无法部署。

---

## 各版本对比总结

| 特性 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|----------|--------|--------|
| 连接模型 | 短连接 | 持久连接 | 持久连接+多路复用 | QUIC 连接+多路复用 |
| 传输层 | TCP | TCP | TCP | QUIC (UDP) |
| 数据格式 | 文本 | 文本 | 二进制帧 | 二进制帧 |
| 头部压缩 | 无 | 无 | HPACK | QPACK |
| 多路复用 | 无 | 管线化（有队头阻塞） | Stream（有 TCP 队头阻塞） | Stream（无队头阻塞） |
| 连接建立 | 每请求握手 | Keep-Alive 复用 | 2 RTT (TCP+TLS) | 1 RTT / 0 RTT |
| 服务端推送 | 无 | 无 | 有 | 有 |
| 连接迁移 | 无 | 无 | 无 | Connection ID |
| 头部加密 | 无 | 无 | 无 | 有 |

---

## 演进本质

```
HTTP/1.0 → HTTP/1.1：解决"连接建立成本"——复用 TCP 连接
HTTP/1.1 → HTTP/2：解决"应用层并发"——多路复用替代串行
HTTP/2  → HTTP/3：解决"传输层瓶颈"——用 QUIC 替代 TCP，消除底层队头阻塞
```

每次升级都是在解决前一版本**最深层的瓶颈**：从连接管理 → 并发模型 → 传输协议本身。HTTP/3 选择"在 UDP 上重新造轮子"而非改进 TCP，正是因为 TCP 的有序字节流语义与多路复用的需求存在根本矛盾，修补不如重写。

# HTTP vs SSE vs WebSocket：实时通信方案选型

## 协议定位速览

```
请求方向：    客户端 ──请求──→ 服务端      （HTTP 请求-响应）
             客户端 ←──推送── 服务端      （SSE 服务器推送）
             客户端 ←──推送──→ 服务端      （WebSocket 全双工）

底层关系：
  HTTP  —— 请求-响应模式，短连接 / 长轮询
  SSE   —— 建立在 HTTP 之上，服务端单向推送
  WS    —— 独立于 HTTP 的 TCP 协议，通过 HTTP Upgrade 握手建立
```

## 核心对比

| 维度 | HTTP（短轮询/长轮询） | SSE（Server-Sent Events） | WebSocket |
|------|----------------------|--------------------------|-----------|
| 通信方向 | 客户端→服务端（请求→响应） | 服务端→客户端（单向推送） | 全双工 |
| 协议基础 | HTTP/1.x ~ HTTP/3 | HTTP（标准 GET + `text/event-stream`） | 独立协议（ws:// / wss://），通过 HTTP Upgrade 握手 |
| 连接模型 | 每次请求新建连接 / 长轮询保持挂起 | 单条长连接，服务端持续输出 | 单条长连接，双向帧通信 |
| 数据格式 | 任意（JSON/XML/二进制等） | 纯文本（UTF-8），支持 Event ID 断点续传 | 文本或二进制帧 |
| 自动重连 | 无（需业务层实现） | 内置（浏览器自动重连 + Last-Event-ID） | 无（需业务层实现） |
| 浏览器限制 | 同域名约 6 个并发 | 同域名约 6 个连接 | 无特殊限制 |
| 服务端推送 | 不支持（需轮询模拟） | ✅ 原生支持 | ✅ 原生支持 |
| 实现复杂度 | 极低 | 低（浏览器 EventSource API） | 高（需管理握手、心跳、帧解析） |
| 防火墙友好 | ✅ 完全兼容 HTTP | ✅ 完全兼容 HTTP | 部分环境会拦截 ws:// |

## 应用场景与选型理由

### 什么时候用 HTTP（轮询）？

**场景：简单数据获取、低频查询、REST API**

- 仪表盘每隔 30 秒刷新一次数据
- 搜索建议输入框的 debounce 请求
- 任何不需要"实时"的业务接口

**为什么不用 SSE / WebSocket？**
- 需求本身是"客户端主动查询"，不是"服务端推送"
- 请求-响应模型最自然，缓存、CDN、中间件生态完善
- 连接不持久，资源开销低
- 过度工程化——为简单查询引入长连接是很大的浪费

### 什么时候用 SSE？

**场景：服务端单向推送，客户端只消费不生产**

- **消息通知**：新邮件提醒、系统告警推送
- **数据流式输出**：AI 聊天流式响应（如 ChatGPT 打字机效果）、日志实时 tail
- **实时行情**：股票价格、加密货币汇率（只展示不交易）
- **状态监控**：服务器健康检查、CI/CD 构建进度推送

**为什么用 SSE 而不是 WebSocket？**

| 理由 | 说明 |
|------|------|
| **更简单** | 浏览器用 `new EventSource(url)` 三行代码搞定，无需管理握手、心跳、重连逻辑 |
| **自动重连** | SSE 内置重连机制 + `Last-Event-ID` 断点续传，WebSocket 需要手写 |
| **天然过 HTTP** | 走标准 HTTP 端口，不会被防火墙/代理拦截；SSE 响应可以被 CDN 缓存（通过 `Cache-Control` 控制） |
| **足够用** | 如果只需要服务端→客户端，双向通信是浪费的——增加了复杂度但没有带来收益 |
| **流式友好** | SSE 天然支持 stream 模式，适合 AI 响应的逐 token 输出 |

**什么时候不该用 SSE？**
- 需要客户端频繁向服务端发送数据（如聊天、游戏操作）
- 需要传输二进制数据（如实时视频帧、音频流）
- 低版本浏览器兼容要求（IE 全系不支持）

### 什么时候用 WebSocket？

**场景：双向实时通信，客户端和服务端频繁互发**

- **即时聊天**：微信网页版、Slack、Discord
- **多人协作**：Google Docs 实时协同编辑、FigJam 白板
- **实时游戏**：多人对战、棋牌类、位置同步
- **金融交易**：下单、撤单、实时盘口深度
- **IoT 设备通信**：设备状态上报 + 远程控制指令下发

**为什么用 WebSocket 而不是 SSE 或 HTTP？**

| 理由 | 说明 |
|------|------|
| **全双工必要** | 聊天场景下，客户端发消息和服务端收消息同样频繁，SSE 的单向能力无法满足 |
| **延迟要求高** | WebSocket 握手后直接走 TCP 帧，无 HTTP 头部开销，延迟更低 |
| **二进制支持** | WebSocket 原生支持二进制帧，适合 protobuf、MessagePack 等高效序列化 |
| **无连接数限制** | WebSocket 不受浏览器 6 连接限制，适合大量通道的场景 |

## 决策流程

```
需要服务端实时推送？
├── 否 → HTTP 请求-响应（简单查询、REST API）
└── 是 → 需要客户端也实时发送数据？
    ├── 否 → SSE（通知、行情、流式输出）
    └── 是 → WebSocket（聊天、协作、游戏）
```
